cljjev Source on GitHub

The model fills in bubbles. Code writes the program.

cljjev builds small Clojure functions from a one-line spec and a few tests. A language model answers one multiple-choice question for each empty slot, and every option on the sheet is legal code.

Why not let the model write the code?

      

        

          
A model that writes text

          
    
            
  • It can call functions that do not exist, or use names that are not bound.
    • 
            
  • It can give a different program each time you ask.
    • 
            
  • Nothing checks the result until you run it yourself.
    • 
          

        

        

          
A model that only chooses

          
    
            
  • Code lists the legal options for each slot. The model picks one.
    • 
            
  • Invented functions, unbound names and wrong arity cannot appear.
    • 
            
  • Every program runs against the tests. Tests decide if it is correct, not the model.
    • 
          

        

      

    


    

      
Every slot is a question with only legal answers

      

        

          
A program is plain Clojure data. An empty slot is a hole. For each hole, ordinary
            code works out what may go there: the names in scope, the kind of value the slot
            needs, and whether it sits in tail position. The model sees the spec, the tests and
            the partial program, and picks one option.

          
Because the rules live in code, they hold for every program. A Lean 4 model of the
            generator proves them:

          
    
            
  • Every name the program uses is bound.
    • 
            
  • recur appears only in tail position, with the right number of arguments.
    • 
            
  • Every function is called with the right number of arguments.
    • 
          

        

        

          
(defn factorial [n]
  (if   ))

          
This slot needs a true or false value. The sheet offers 30 options,
            such as (zero? _), (<= _ _) and (empty? _).
            A collection is never offered where a number goes, and a name that is not in scope
            is never offered at all.

        

      

    


    

      
When the tests fail, the search repairs the program

      
    
        
  1. Read the tests
    The (= ...) forms in the spec become
          tests. They also fix the function's name, its arity and the kind of each parameter.
    2. 
        
  2. Build
    Holes are filled left to right, one question each, as in the
          sheet above.
    3. 
        
  3. Test
    The finished program runs against every test in a separate
          process with a time limit, so a program that never stops cannot hang the search.
    4. 
        
  4. Trace and score
    Each test runs again with a spy around every chosen
          subtree. The model rates each subtree from wrong to correct, and it sees what the
          subtree computed on the passing and the failing tests.
    5. 
        
  5. Edit
    Suspect subtrees get edits: the next-best option, a swap of two
          arguments, or a wrap that keeps the half-right code and adds the missing part.
    6. 
        
  6. Search
    Edits are tried in order of probability times suspicion. An
          edit rebuilds only its own subtree, and every other choice is replayed. The first
          program also gets a few restarts: a close runner-up at one decision, with every later
          slot asked again, so the search can try a different shape.
    7.

What it does today

      
Two live runs of the latest version with the Jev
        model, on two sets of specs. The model's answers change between runs, so results can differ.

      

        
Spec setPassedAPI calls per run

        
          
Basic: factorial, fib, reverse, clamp and 11 more15 of 15142 to 218

          
Hard: gcd, take-n, dot product, prime? and 10 more11 of 14443 to 580

        
      

      

        
Small language
About 36 core functions and the forms defn fn let
          loop recur if when cond if-let do. No maps, destructuring or Java interop yet.

        
Weak tests let wrong programs pass
With only (= 55 (fib 10)),
          the search once returned the sum 1 + 2 + … + n. Specs need tests that rule out shortcuts.

        
Answers vary between runs
When two options are close, the same spec can
          pass in one run and fail in the next.

        
Finding the wrong part is hard
Most failures happen when the model rates
          the broken subtree as plausible, so the search never edits it.

      

    


    

      
Try it

      
You need the Clojure CLI and Babashka. Without an
        API key, the same search runs with a simple offline policy.


git clone https://github.com/esshka/clj-synth.git
cd clj-synth
export JEV_API_KEY=...        # optional
clojure -M:run "write a recursive factorial of n (= 120 (factorial 5)) (= 1 (factorial 0))"
